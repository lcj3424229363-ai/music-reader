## TL;DR

P22.5-B 是 Score Model (谱面文档态), 跟 P22.3 editorState (输入态) 并存。要做的 5 件事:
1. Score 文档层 (parts/staves/voices/measures)
2. Part 抽象 (大谱表多声部)

4. 节奏单位 (units vs Fraction)
5. VF 边界 (Renderer 隔离)

## 决策 1: measure 粒度 — per voice vs per staff

**现状** (摸底):
- `scoreMeasures[i]` 顶层数组, 每 measure 一个
- 大谱表: `staffScores.treble.measures[i]` / `bass.measures[i]`
- 跨声部 measure 同步由用户操作保证, 没有"同 measureIndex = 同一时间"约束

**选项**:
- **A. per voice (1 measure 1 voice 1 entries)**: 顶层 `score.measures[i].voices[voiceId].entries`
  - 优势: 跨声部对齐显式建模, 大谱表结构清晰
  - 劣势: 单谱表冗余 (voices 数组只有 1 个)
- **B. per staff (1 measure 1 staff 1 entries)**: `score.staves[staffId].measures[i].entries`
  - 优势: 单谱表 = 1 staff, 简单
  - 劣势: 大谱表仍然 per staff, 跨 staff 对齐靠 measureIndex 隐式
- **C. 混合 (顶层 measures + 每 measure 多个 voices)**: 跟 A 类似, 但 measure 是顶层
  - 优势: 单谱表无冗余, 大谱表有 voices 数组
  - 劣势: 大谱表实现复杂

**我推荐**: **A — per voice**。因为:
- 大谱表是核心场景 (双谱表 4 voice)
- per voice 后跨声部对齐显式 (`measure.voices[1].entries[0]` 和 `measure.voices[2].entries[0]` 是同一时间)
- 单谱表冗余可接受 (voices 只有 1 元素)
- 跟 MusicXML `<part><measure><voice>...</voice></measure></part>` 一致

## 决策 2: 跨 measure 关系 — reference (id) vs 嵌套

**现状**:
- `entry.tieStart: boolean` — 不知道 target 在哪
- `entry.slurStart: boolean` — 同上
- 跨 measure 关系**没建模**

**选项**:
- **A. reference (id)**: 每个 entry 有唯一 `id`, 跨 measure 关系用 `{type: "tie", from: "id1", to: "id2"}`
  - 优势: 关系独立, 验证/转换/序列化解耦
  - 劣势: 多一层 lookup
- **B. 嵌套**: 关系挂在 from entry 上 (`entry.tieTo: "id"`)
  - 优势: 关系跟 from 一起, 查询快
  - 劣势: 验证双向一致性 (tieTo 跟 tieFrom) 复杂
- **C. 当前 boolean + 跨 measure 临时查询** (现状, 不动)
  - 优势: 0 改动
  - 劣势: A.3 跨 measure 实现里这个查询逻辑散在 draw* 函数里, 不可维护

**我推荐**: **A — reference (id)**。理由:
- 显式关系可验证 (`tie` 的 from/to 必同音高)
- 序列化干净 (JSON)
- 跟 MusicXML `<tie type="start"/>` / `<tie type="stop"/>` 对应 (但 MusicXML 是分开的, 我们用 1 个 `tie` 关系对象)
- 老 boolean 字段保留为 derived 缓存 (A.3 跨 measure fallback 用)

## 决策 3: 节奏单位 — `units` (int) vs `Fraction`

**现状**:
- `entry.units: number` — 1 quarter = 8, 1 eighth = 4, 1 sixteenth = 2
- `tupletPosition` / `tupletType` 用 units 算位置
- VexFlow `VF.Fraction(numerator, denominator)` 替代

**选项**:
- **A. 保留 `units: int`**: 1 quarter = 8 (业界乐谱软件标准, Sibelius/Finale 都是这样)
  - 优势: 老代码不动, 算 tuplet 位置简单
  - 劣势: 不是数学分数, 跨 tuplet 处理略复杂
- **B. 改 `VF.Fraction`**: numerator/denominator
  - 优势: 数学严格, VexFlow 原生支持
  - 劣势: 全局重写, MusicXML parser 要改
- **C. 双轨 (units 主 + Fraction 缓存)**: 兼容老代码
  - 优势: 渐进式迁移
  - 劣势: 双源真相风险

**我推荐**: **A — 保留 units**。理由:
- 老代码稳定运行 200+ 测试
- MusicXML parser 解析成 units 已经能跑
- 跨 tuplet 复杂 (3 连音 = 8/3) 用 VexFlow.Fraction 处理局部, 不全局改
- `units` 双源真相风险 (P22.5-A 摸底列的 #8) 可加 sync 验证 (commitEdit 时检查)

## 决策 4: editorState vs Score Model — 并存 vs 替换

**现状**:
- `editorState`: 输入态 (selectedEntryIndex, currentMeasureIndex, mode, etc.)
- 谱面数据: `scoreMeasures[]` (顶层) / `staffScores.treble.measures[]` (大谱表)
- editorState 跟 score 数据**混合** (在 P22.3 重构后)

**选项**:
- **A. 严格分离**: editorState 只管 UI 状态, 谱面数据全在 Score Model
  - 优势: 概念清晰, Score 可序列化/反序列化
  - 劣势: 大改, 跟现有 app.js 集成复杂
- **B. 现状 (混合) + Score Model 影子**: Score Model 是 `scoreMeasures` 的封装层, editorState 仍管 UI
  - 优势: 0 侵入, Score Model 是 view / serialization
  - 劣势: 数据双份 (但单源真实 — 谱面数据真在 `scoreMeasures`, Score Model 是 computed view)
- **C. Score Model 逐步替换**: editorState 重构期作为中间层, 最终用 Score Model 替换
  - 优势: 渐进式
  - 劣势: 中间期两套 API 维护负担

**我推荐**: **B — 现状 + Score Model 影子**。理由:
- 0 侵入, 现有 200+ 测试不破
- Score Model 是**数据契约**, 不替代运行时数据
- 序列化用 Score Model (round-trip 可验证)
- P22.6 之后 (Renderer 分离) 再考虑 C

## 决策 5: VexFlow 边界 — 隔离 vs 渗入

**现状**:
- `web/app.js` 直接用 `VF.Articulation`, `VF.StaveTie`, `VF.Curve`, `VF.RehearsalMark` 等
- 100+ 处 VF.* 调用
- Score Model 字段命名 (articulation/slurStart 等) 跟 VexFlow 1:1 对应 (隐含耦合)

**选项**:
- **A. 严格隔离**: Score Model 字段是 VexFlow-agnostic (articulation → enum `staccato|accent|...`), Renderer 翻译
  - 优势: Score Model 不依赖 VexFlow, 可换渲染 (OSMD, Verovio)
  - 劣势: 大改 — 字段命名 + 翻译层
- **B. 半隔离**: Score Model 字段名沿用 VexFlow 习惯 (articulation), 但 Renderer 是唯一允许的 VF 使用方
  - 优势: 字段重命名工作量小, Renderer 仍可换
  - 劣势: 字段名硬耦合 VexFlow 习惯
- **C. 不隔离 (现状)**: app.js 全是 VF.*
  - 优势: 0 改动
  - 劣势: Score Model 永远绑死 VexFlow

**我推荐**: **B — 半隔离**。理由:
- 字段名跟 VexFlow 习惯 (articulation/ornament/slurStart 等) 用户已经熟
- "Renderer 是唯一 VF 使用方" 这条规则**容易执行** (P22.6 收口)
- 翻译层只在 Score Model 的 export 端 (P22.6) 加, 不在字段命名
- A 方案换 renderer 概率 < 5%, 不值得大改
