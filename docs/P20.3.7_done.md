### 3.4 验证流程

下载到 mxl 后：
1. `music21.corpus.parse(path)` 加载
2. 检查 n_measures, key, time_signature

4. 与 gold JSON 的 `analysis.key` 对比 — 不一致则 mark conflict

## 4. Annotation Plan (拿到谱面后)

### 4.1 三层标注

| 层 | 内容 | 标注者 | 工具 |
|---|---|---|---|
| L1: **Score Layer** | 原始 mxl 文件 | (已存在) | MuseScore / Dorico |
| L2: **Harmonic Annotation** | 每小节的罗马数字 + 功能 + cadence | human/music 理论学者 | `annotation.json` |
| L3: **Pedagogical Annotation** | 教学要点 + 错误模式 | human/music 教师 | `pedagogy.json` |

**L2 (Harmonic Annotation) 是 benchmark 的核心标准**。

### 4.2 L2 标注格式

```json
{
  "id": "mozart_k545_m1",
  "score": "mozart_k545.mxl",
  "measure_range": "mm.1-8",
  "annotator": "human/<name>",
  "annotate_date": "2026-...",
  "framework": "sposobin",
  "measures": [
    {
      "m": 1,
      "roman": "I",
      "function": "T",
      "inversion": "root",
      "soprano": "C5",
      "bass": "C3"
    },
    {
      "m": 4,
      "cadence": "HC",
      "comment": "V7 → I 在 m.4, 旋律结束 G4"
    },
    {
      "m": 8,
      "cadence": "PAC",
      "comment": "V7 → I 在 m.8, 旋律结束 C5"
    }
  ]
}
```

### 4.3 标注的"非唯一答案"原则

**音乐理论非唯一答案**。一个 case 在不同 framework 下有不同合法标注：

- Sposobin V1 (V1 默认): 纯 T/S/D
- Schenkerian: 看重骨架 + 延长
- Modal: 看重调式

L2 标注要标**主标注** (framework=sposobin) + 至少 1 个 `alternative_analysis` (例 schenkerian)。

## 5. Schema 改动 (P20.3.7)

### 5.1 新增 Provenance dataclass

在 `data/eval/schema.py` 加：

```python
@dataclass
class Provenance:
    source_score: str = ""          # 例 "mozart_k545.mxl"
    source_url: str = ""            # IMSLP URL
    source_format: str = ""         # "musicxml" / "midi" / "kern" / "pdf" / "mscz"
    measure_range: str = ""         # 例 "mm.1-8"
    annotator: str = ""             # "human/<name>" / "music21-auto" / "ai/<model>"
    annotate_date: str = ""         # ISO 8601
    confidence: float = 0.0         # 0-1
    evidence_chain: list[str] = field(default_factory=list)  # ["music21 corpus", "IMSLP"]
    acquired_status: str = "needs_imslp"  # "available" / "needs_imslp" / "needs_humdrum" / "needs_pdf_ocr"
    review_status: str = "raw"      # "raw" / "human_annotated" / "expert_reviewed"
    notes: str = ""
```

### 5.2 EvalCase 加 provenance 字段

```python
@dataclass
class EvalCase:
    metadata: Metadata
    analysis: Analysis
    ...
    provenance: Provenance = field(default_factory=Provenance)  # P20.3.7 NEW
```

### 5.3 新 helper 函数

- `find_needs_provenance()` — 返回所有没谱面的 case

- `find_fully_reviewed()` — 返回完全可进 benchmark 的 case (谱面 + 标注 + expert review 齐)
- `gold_provenance_summary()` — 统计报告

### 5.4 兼容性

## 7. 反思 (P20.3.5 教训)

P20.3.5 我把 6 维度的 review 写成"准审计报告"，对 Bach V6/4 → K6/4、Beethoven vii°7、Haydn m.4 HC 等给了**过高的确定性建议**。

**根本原因**：在没有 MusicXML 的情况下，我做的是"经验判断"而非"谱面验证"。

**P20.3.7 教训**：

1. **没有谱面，没有 music theory gold** — 这不是"工作流"问题，是"项目假设"问题
2. **gold benchmark 的可信度 ≠ Agent 的准确率** — 跑分再高，如果 gold 错了，等于 Agent 在向幻觉对齐
3. **"工程层冲突"和"音乐理论冲突"必须分离** — 前者 99% 可自动化，后者必须谱面 + 人工
4. **领域知识没有捷径** — 音乐 AI benchmark 必须按"谱面 → 标注 → 评测"流程，不是"猜 → 标 → 评测"

**未来 P20.4+ 的红线**：
- ❌ 不直接修改 gold JSON 的音乐内容 (roman_progression, functional_analysis, cadences) — 这些都需要谱面验证
- ✅ 可以修改工程层字段 (analysis_framework, measure_range 与 excerpt 冲突, type 错别字)
- ✅ 必须先完成 provenance 三个阶段 (available → human_annotated → expert_reviewed) 才能进 benchmark
- ✅ benchmark 跑分报告必须标"gold 状态"，例如 "8/8 gold 都是 needs_imslp 状态，benchmark 结果仅供参考"

## 10. 总结

P20.3.7 = "承认问题" + "建立 evidence chain"。

**之前的错误**：把"我手写的猜测"当 "gold standard"。

**现在的状态**：
- 8 个 gold 全部明确标记 `acquired_status: needs_imslp` (无谱面)
- schema 加了 Provenance 字段，强制每个 gold 必须有 evidence chain
- 19 个 P20.3.7 单测保证：
  - 8/8 gold 必须有 provenance 字段
  - 0/8 fully reviewed → benchmark 暂停
  - JSON 序列化往返不丢失

**对 MTRE 项目的影响**：
- benchmark 暂停跑（因为 0/8 gold 是"可信赖的"）
- 下一个里程碑 = P20.4 (Score Acquisition)
- 没有 P20.4 (谱面) → P20.5 (标注) → P20.6 (专家审定) → P20.7 (Benchmark Runner) 不能跳

**这是痛苦的但必要的刹车。** Music AI project 死在 "Agent 越训越像错的 gold" 上的项目比死在 "算力不够" 上的多得多。
